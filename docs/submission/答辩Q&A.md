# 答辩 Q&A 预案

> 按「最可能被问」排序。答案全部基于仓库里的真实实现，可以用代码指认。
> 遇到不会的，就承认边界并说清下一步 —— 比硬编更好。

---

### Q1. 这和 ChatGPT 的记忆功能、或者带记忆的笔记工具有什么区别？

**一句话**：他们记的是「对话片段」，我们记的是「可确认、可追溯、可修改的结构化事实」，并且这些事实会驱动执行。

具体三点：

1. **确认机制**：抽取结果先作为草稿进入待确认列表，用户点确认才落库；模型不能直接把猜测写进档案。
2. **双向可追溯**：每条记忆有 `sourceMemoryId`，能反查来源；删除是双向对称的（删记忆级联删节点，删目标级联删来源记忆）。
3. **驱动执行**：记忆确认后立刻生成目标/任务/事件，进入日程与复盘；不是"存起来等你搜"。

### Q2. 模型会不会瞎编用户的记忆？你们怎么防？

三层防线：

1. **提示词层**：明确「绝不编造没说过的信息」「不确定就把置信度降到 0.6 以下，memory 可以为 null」。
2. **服务端校验层**：输出逐字段归一化——类型必须在枚举内、日期必须是 `YYYY-MM-DD`、时长夹在 0.5–12 小时、置信度夹在 0.3–1，不合法的字段直接丢弃（`server/agent.ts` 的 `normalizeModelOutput`）。
3. **产品层**：默认不自动确认，必须用户点确认卡片；设置里的「自动确认」是显式开关，默认关闭。

### Q3. 为什么用知识图谱，而不是向量检索（RAG）？

两者解决不同问题，我们用的是图谱，但**不排斥以后加向量**：

- 向量擅长「找相似文本」，回答"我以前说过什么关于 X 的事"。
- 图谱擅长「表达关系」，回答"这个目标和我正在做的事、认识的人是什么关系"。
- 产品的核心动作是**建立关系**（目标↔任务↔事件↔人），这是图结构天然的表达；而且图谱可以被用户直接看见和修改，向量库做不到。

规模上去以后，检索层可以换成「图谱 + pgvector 混合」，但 MVP 阶段的图谱是更诚实的选择。

### Q4. 用户隐私怎么保证？数据会不会上传？

当前实现：

- 记忆、对话、图谱**只存在设备本地**（AsyncStorage），没有账号、没有云端同步。
- 模型密钥只在服务端，客户端拿不到。
- 发往服务端的上下文**按需裁剪**：最近 12 条记忆、活跃目标、未完成待办、节点名——不做全量同步（`services/ai/remoteAgent.ts`）。
- 用户可以随时「清空我的数据」，清空后回到只有「我」一个节点的空白图谱。

需要改进的地方：目前没有数据导出与端到端加密，这是路线图里明确列出的项。

### Q5. 为什么自己写 Agent 服务，不用 LangChain / LangGraph？

因为这个链路的复杂度只有三件事：**拼提示词、调一次模型、校验输出**。

- 引入框架会带来看不见的控制流（回调、状态机、隐藏重试），调试成本高于收益。
- 我们的约束是「输出必须是可校验的 JSON」，一层的确定性代码反而更容易写测试——现在的 39 个单测里，Provider 与归一化占了 15 个。

真正需要编排（多步骤、多工具、长任务）时再引框架，而不是一开始就付这个成本。

### Q6. 成本多少？能撑住真实用户吗？

抽取类请求很短：一次约 600 input + 150 output token。

按 DeepSeek V4.1 Flash 的价格（输入 $0.15 / 1M，输出 $0.6 / 1M，非高峰）：

- **一次对话 ≈ $0.0002**（约 0.0015 元），1000 次对话约 1.5 元。
- 22 条评估用例实测成本约 $0.002。

真正贵的是"每次把全量记忆塞进上下文"，所以上下文做了裁剪；再往后可以加缓存（同一会话前缀命中缓存，价格降到 1/50）。

### Q7. 如果模型换了 / 断网了 / 没配 key 呢？

- **可替换**：`AGENT_MODEL` + `AGENT_BASE_URL` 一行切换，任何 OpenAI 兼容端点都能接（DeepSeek / OpenAI / Kimi / GLM / 硅基流动）。
- **可降级**：服务不可用时客户端自动回落本地规则引擎，并在 UI 提示「已用本地引擎回复」，界面不会卡死。
- **可离线**：不配 `.env` 时整个 App 仍可用，只是语言理解变成关键词规则。

这是刻意的设计——**模型是增强项，不是单点依赖**。

### Q8. 22/22 的准确率是你们自己出的题，可信吗？

不可全信，所以要说清三件事：

1. 这 22 条**不是为了刷分写的**：8 类记忆各 2–3 条，另外 4 条是"不该记"的负例（寒暄、情绪、知识提问、高风险操作）——负例是最容易翻车的部分。
2. 首轮真实成绩是 **20/22**，两个错例（"今天下午四点开组会"判成 event、"我看完了《人类简史》"判成 interest）暴露的是提示词缺边界，加规则后到 22/22。**这个过程本身就是证据**。
3. 它是回归网，不是能力证明：真实用语一定更脏。下一步是把用户真实语料加进 `cases.ts`，并把阈值卡在 80% 防止退化。

### Q9. 商业模式是什么？

MVP 阶段不设计变现，但方向上：

- 个人版订阅（记忆容量 / 主动服务 / 多设备同步）；
- 企业版授权（团队知识图谱 + 合规审计）；
- **不做的**：卖用户数据、卖注意力（推送广告与我们"低打扰"原则直接冲突）。

---

### Q10. 用户凭什么愿意把自己的信息录进来？

1. **先给价值再要信息**：三问引导之后立刻产出可见的图谱与目标，不是先填一张表单。
2. **数据不出设备**：本地存储 + 可一键清空，是能说出口的承诺。
3. **可纠正**：说错了可以改、可以删，删得干净——信任来自"后悔权"。

### Q11. 冷启动时（什么记忆都没有），这个产品还有用吗？

有，但价值要重新定义：

- 空图谱时，Agent 走"引导式提问"（三问 + 快捷动作），帮助用户说出第一件事。
- 统计与复盘在零数据下不报错、不出假数字（有专门的空数据测试）。
- 第一周的价值是"帮你把想法变成可执行的日程"，第二周才开始体现"记得你"。

这也是为什么我们把演示数据做成**手动载入**：新用户不该看到别人的记忆。

---

### Q12. 主动提醒会不会变成骚扰？

我们写进产品约束的四条：有真实上下文、有明确价值、**低打扰**、可关闭。

具体做法上，优先"事件驱动"而不是"定时推送"：任务到期、目标停滞、连续未完成才触发；用户不回应就降频，不做连续追问。

---

### Q13. 为什么是 App 不是纯 Web / 小程序？

- 短期：目标用户（大学生）主要在手机上，通知、语音、健康数据都在移动端。
- 技术：Expo 一套代码同时产出 iOS / Android / **Web**，评委可直接用浏览器体验，不需要装包。
- 长期：KnowMe 的终局是"跨设备个人智能层"，App 只是第一个交付形态。

---

### Q14. 团队人少，怎么保证质量？

用**门禁**代替人肉 review：

- `npm run verify` = typecheck + lint + 39 个单测，提交前必过。
- CI 在 Ubuntu 上跑**真实打包**——这一步抓到了「文件名大小写不一致」这种 Windows 本地永远看不见的问题（原提交在 Linux 上直接构建失败）。
- 模型能力用 22 条用例回归，低于 80% 直接红。

---

### Q15. 下一步最重要的一件事是什么？

**把"复盘结论"写回记忆**。

现在复盘能生成下周计划（任务），但"这周我发现自己晚上效率低"这类结论还没进入记忆层。
补上之后，闭环才真正变成"每一轮都更懂你"，而不只是"每一轮都有新任务"。
